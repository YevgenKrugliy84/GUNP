# Рекомендації з модернізації

Контекст: проєкт переписано з Flask (2053-рядковий `app.py` + мертвий, зламаний `admin.py`)
на Django. Нижче — що вже виправлено при переписуванні, і що варто зробити далі, якщо
проєкт піде в реальну експлуатацію.

## Вже виправлено при переписуванні

- **Втрата даних при кожному рестарті.** Стара `app.py` виконувала
  `os.remove('gundatabase.db')` при кожному старті застосунку — це буквально й було
  причиною того, що в реальній БД лишилися тільки 25 підрозділів і 0 записів/заявок.
  Нова версія створює БД один раз; дані зі старої БД перенесені ідемпотентною командою
  `import_legacy_db`, яку можна запускати повторно без дублювання.
- **Мертвий, зламаний код.** `admin.py` ніде не імпортувався і посилався на неіснуючі
  імена (`current_user`, `logging`, `abort`, `User` — жодне не імпортовано у файлі).
  Видалено.
- **Windows-only traceroute на Linux-сервері.** `network_tools()` завжди викликав
  `tracert`, якого немає на Linux — команда мовчки падала. Тепер вибір `tracert`/`traceroute`
  залежить від `os.name`, як і було зроблено для ping.
- **700+ рядків ручних CRUD-роутів** (додати/редагувати/видалити підрозділ/запис/заявку/
  статтю/користувача) замінені вбудованою Django-адмінкою — менше коду, менше місць для
  дублювання помилок валідації, готовий журнал дій (`django.contrib.admin.LogEntry`), якого
  у старій версії не було взагалі (зміни ніхто не відстежував).
- **Крихкий формат приватного чату.** Стара модель кодувала одержувача як префікс рядка
  (`f'dept_{target_id}'`) і в кількох місцях викликала `.startswith('dept_')` на значенні,
  яке могло бути `None` — потенційний `AttributeError`. Замінено на явні поля
  `recipient_kind`/`recipient_id`.

## Що варто зробити перед реальним продакшн-запуском

1. **Секрети.** `SECRET_KEY` і пароль адміністратора зараз читаються з `.env`
   (`gunp_django/.env.example`) із dev-заглушками за замовчуванням. Перед реальним
   деплоєм — обов'язково задати власний `DJANGO_SECRET_KEY` і **змінити пароль
   `PowerEdge123`** одразу після першого входу. Розгляньте секрет-менеджер
   (Vault, systemd-credentials, тощо) замість файлу `.env` на проді.
2. **Сервер застосунку.** `manage.py runserver` — це dev-сервер, не розрахований на
   продакшн-навантаження й конкурентні з'єднання. Для реального використання —
   `gunicorn` (або `waitress` на Windows) за `nginx` як reverse proxy, з `DEBUG=False`
   і правильно виставленим `STATIC_ROOT`/`collectstatic`.
3. **Обмеження спроб входу.** Ні стара, ні нова версія не мали захисту від брутфорсу
   пароля адміністратора. Додайте `django-axes` або аналог (лока після N невдалих спроб).
4. **Пінг-статуси підрозділів.** Зараз перевірка живості обчислюється на льоту при
   кожному запиті `/department-statuses/` (той самий підхід, що й у старій версії для
   адмінки, але тепер публічно). При зростанні кількості підрозділів це варто перенести
   у фоновий job (Celery beat, `django-crontab`, або systemd timer, що раз на 5 хв.
   викликає management-команду) і віддавати вже закешований статус — так, як за задумом
   мала працювати `BackgroundScheduler` у Flask-версії (яка була підключена, але
   толку з неї було мало, бо кожен рестарт стирав саму базу).
5. **Чат: presence і "хто онлайн".** Свідомо не перенесено — Socket.IO давав живий
   список онлайн-користувачів через `join_room`/`online_users`; AJAX-polling (кожні 3с)
   цього не дає. Якщо presence/typing-indicators стануть реальною вимогою — це привід
   перейти на Django Channels + Redis channel layer, а не робити це заздалегідь заради
   малонавантаженого внутрішнього чату.
6. **Приватний чат адміністратора.** Поточна реалізація ідентифікує приватний тред
   ID користувача-не-адміна; сторінка `/chat/` поки не має явного списку "з ким з
   користувачів веде розмову адмін" (в оригіналі це збиралося вручну через словник
   `conversations` у Python). Варто додати admin-side список активних тредів
   (наприклад, окрема Django admin ModelAdmin-вьюха над `PrivateChatMessage`, згрупована
   по `recipient_id`, або невеликий кастомний view).
7. **Швидкість/спідтест.** `speedtest-cli` синхронно блокує воркер на час тесту (десятки
   секунд) — прийнятно для одного адміністратора, але при паралельних запитах варто
   винести в фонову задачу (Celery/RQ) з опитуванням статусу з фронтенду.
8. **Залежності.** Зафіксовані версії (`requirements.txt`) варто регулярно перевіряти
   `pip-audit`/`safety` — Flask-версія мала непінові індиректні залежності
   (`speedtest-cli`, `apscheduler`), що з часом накопичує вразливості без сповіщення.
9. **HTTPS.** І стара, і нова версія розраховані на HTTP на внутрішній мережі
   (`10.111.16.6:4040`). Якщо портал стане доступним ширше внутрішньої підмережі —
   потрібен TLS-термінатор (nginx/traefik) і `SECURE_SSL_REDIRECT=True`.
10. **Резервне копіювання.** SQLite підходить для невеликого внутрішнього інструмента,
    але не має вбудованого реплікаційного/бекап-механізму. Мінімум — щоденний `cron`,
    що копіює `db.sqlite3` кудись поза сервером; за зростання навантаження — перехід на
    PostgreSQL (Django підтримує це заміною `DATABASES` без зміни моделей).
