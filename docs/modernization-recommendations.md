# Рекомендації з модернізації

Контекст: проєкт переписано з Flask (2053-рядковий `app.py` + мертвий, зламаний `admin.py`)
на Django, розгорнуто на продакшн-стеку (gunicorn + nginx + systemd) на `10.111.16.6:8095`.
Нижче — що вже зроблено, і фазована дорожня карта того, що робити далі.

## Вже зроблено

**Переписування та виправлення багів:**
- **Втрата даних при кожному рестарті.** Стара `app.py` виконувала
  `os.remove('gundatabase.db')` при кожному старті — саме тому в реальній БД лишилися
  тільки 25 підрозділів і 0 записів/заявок. Нова версія створює БД один раз; дані зі
  старої БД перенесені ідемпотентною командою `import_legacy_db`.
- **Мертвий, зламаний код.** `admin.py` ніде не імпортувався і посилався на неіснуючі
  імена (`current_user`, `logging`, `abort`, `User`). Видалено.
- **Windows-only traceroute на Linux-сервері.** Виправлено вибір `tracert`/`traceroute`
  залежно від `os.name`.
- **700+ рядків ручних CRUD-роутів** замінені вбудованою Django-адмінкою — плюс журнал
  дій (`LogEntry`), якого раніше не було взагалі.
- **Крихкий формат приватного чату** (`f'dept_{id}'`-рядки з ризиком `AttributeError`)
  замінено на явні поля `recipient_kind`/`recipient_id`.
- **CSRF-помилка на чат-боті** (`Origin checking failed`) після переходу на порт `8095` —
  виправлено додаванням `CSRF_TRUSTED_ORIGINS`.

**Інфраструктура (продакшн-деплой на цьому хості):**
- gunicorn (`gunp.service`, systemd, автозапуск/автовідновлення) за nginx
  (`10.111.16.6:8095`), `DEBUG=False`, реальний згенерований `SECRET_KEY`.
- `logrotate` для логів gunicorn (щотижня, 8 ротацій, коректний reopen через `SIGUSR1`).
- Правило `ufw` для порту `8095`, узгоджене з підмережами інших сервісів УІАП на хості.
- Пароль адміністратора змінено з дефолтного; `create_default_admin` більше не хардкодить
  пароль — генерує випадковий, якщо `GUNP_ADMIN_PASSWORD` не задано.

**UI/UX:**
- Адмінка переведена на `django-jazzmin` — брендована (`GUNP — Адмінпанель`), іконки по
  моделях, підтримка темної теми.
- Оновлено дизайн публічної частини: сучасніша типографіка (Manrope), картки підрозділів
  з hover-ефектом, м'які тіні/радіуси, липка навігація — синьо-жовта символіка збережена,
  але без застарілого смугастого фону та суцільних капслоків у навігації.

**Фаза 1 (виконано):**
- **Обмеження спроб входу** — `django-axes`, 5 невдалих спроб → lockout на 1 год.
  (username+IP). Довелось окремо виправити визначення реальної IP клієнта через
  `X-Real-IP` — без цього axes бачив усіх користувачів як одну IP (`127.0.0.1` від nginx)
  і заблокував би всіх одразу після 5 невдалих спроб будь-кого.
- **Резервне копіювання БД** — щоденний systemd-timer (`03:15`, `backup-gunp-db.timer`),
  безпечний online-бекап через `sqlite3.backup()` (Python stdlib, без нової системної
  залежності), gzip, зберігання 30 днів. **Обмеження:** бекап локальний (той самий диск) —
  захищає від випадкового пошкодження/видалення даних, але не від відмови диска/хоста;
  справжній офсайт-бекап (інший хост/сховище) поки не налаштований.
- **Аудит залежностей** — `pip-audit` знайшов 10 відомих CVE в Django 5.0.14 (гілка вже не
  підтримується). Оновлено до Django 5.2 LTS, повторний аудит — 0 вразливостей. Вартий
  повторення раз на квартал.
- **Права на `.env`** звужено до `600` (лише власник) — раніше файл із `SECRET_KEY` був
  читабельний групою/усіма.
- **`SECRET_KEY`/паролі — у секрет-менеджер** — усе ще не зроблено (`.env`-файл на диску
  сервера); виправдано відкласти, поки до сервера має доступ лише одна довірена особа.

### Фаза 2 — операційна видимість (виконано)

- **Healthcheck-ендпоінт** — `/healthz/` (перевіряє доступність БД, `503` при відмові),
  плюс `check-gunp-health.timer` кожні 5 хв. опитує його і сповіщає лише після 3
  послідовних невдач (щоб не спамити на одиничний збій).
- **Окремі nginx-логи для GUNP** — `gunp_access.log`/`gunp_error.log` замість спільних
  файлів з іншими сайтами хоста; підхоплюються вже наявним `logrotate`-конфігом nginx
  (`/var/log/nginx/*.log`), окремого налаштування ротації не знадобилось.
- **Сповіщення про збої** — `OnFailure=gunp-alert@%n.service` на `gunp.service` і
  `backup-gunp-db.service`: завжди пише гучний запис у journal (`journalctl -t
  gunp-alert`) і шле `wall` залогіненим сесіям; опційно постить у вебхук
  (`GUNP_ALERT_WEBHOOK_URL` у `/etc/default/gunp-alerts`, не закомічено — точка
  розширення на майбутнє, коли з'явиться реальний канал сповіщень типу Telegram/Slack).
- **Знайдений і виправлений реальний баг деплою:** зміна Python-коду без явного
  `systemctl restart gunp` (окремо від `install.sh`, який навмисно не рестартує
  вже активний сервіс) залишає воркерів gunicorn у неконсистентному стані — кожен
  воркер ліниво імпортує код при своєму першому запиті незалежно, тож частина
  запитів обслуговується новим кодом, частина — старим, поки не станеться повний
  рестарт. Задокументовано в README як обов'язковий крок деплою.

### Фаза 3 — функціональність і UX

Коли базова надійність не викликає сумнівів — розвивати сам продукт:

- **Приватний чат адміністратора**: додати список активних тредів на стороні адміна
  (зараз це доводиться визначати вручну — див. пункт нижче в "залишкових обмеженнях").
- **Пінг-статуси підрозділів у фоні** замість обчислення на кожен запит
  `/department-statuses/` — `django-crontab`/systemd-timer раз на кілька хвилин,
  результат кешується в БД (модель `Department` вже має поля `last_status`/`last_latency`
  саме для цього).
- **Спідтест — у фонову задачу** (Celery/RQ), бо зараз він синхронно блокує gunicorn-воркер
  на десятки секунд при кожному запуску.
- **Автотести.** Проєкт наразі не має жодного автотесту (ні у Flask-версії, ні в Django) —
  навіть базові smoke-тести (Django `TestCase` на ключові вьюхи: логін, створення запису,
  відправка заявки) різко знизять ризик регресій при подальших змінах.

### Фаза 4 — архітектурні інвестиції (робити тільки за реальної потреби)

Це свідомо відкладено — додавати інфраструктурну складність варто лише коли з'явиться
конкретна вимога, а не про запас:

- **Presence у чаті** ("хто онлайн", typing-indicators) — Django Channels + Redis
  channel layer замість поточного AJAX-polling. Не варто робити завчасно для
  малонавантаженого внутрішнього чату.
- **PostgreSQL замість SQLite** — якщо навантаження/кількість підрозділів суттєво
  зросте, або знадобляться конкурентні записи з кількох процесів одночасно (Django
  підтримує це заміною `DATABASES` без зміни моделей).
- **TLS/HTTPS** — якщо портал вийде за межі внутрішньої підмережі `10.111.16.0/24`
  й сусідніх, потрібен TLS-термінатор (nginx/traefik) і `SECURE_SSL_REDIRECT=True`.
- **Контейнеризація (Docker)** — якщо з'явиться потреба розгортати на іншому хості
  чи в кількох середовищах (staging/prod); для одного внутрішнього сервера, який вже
  працює, це радше ускладнення, ніж вигода просто зараз.

## Залишкові свідомі обмеження (не баги, а прийняті рішення)

- **Presence-статус у чаті** ("хто онлайн") не перенесено з Socket.IO — див. Фазу 4.
- **Приватний чат адміністратора** поки не має явного списку "з ким із користувачів
  веде розмову адмін" (в оригіналі це збиралося вручну в Python-словнику) — див. Фазу 3.
